Side-by-side

ressrf-go vs ressrf PR #25

Two independent Go ports of the same Rust ressrf-core SSRF engine. local = this repo (timescale/ressrf-go) · PR #25 = new go/ressrf-static in timescale/ressrf.

Same problem, two designs. PR #25 adds go/ressrf-static as a sibling to the existing WASM-backed go/ressrf, motivated by binary size and dropping the wazero runtime. This repo is a standalone port that has been iterating longer — it's the source of the codegen pipeline and the differential-fuzz harness, neither of which exists in the PR.

Insight
Two ports of the same Rust core, written without coordination, end up making opposite choices on almost every API axis (typed-iota vs. string presets, sealed-sum reasons vs. string codes, additive WithDenied* + separate constructor vs. single builder with implicit mode-flip). That's the value of the cross-language conformance vectors: they constrain behaviour without dictating shape, so each binding can be idiomatic in its host language while staying observably interchangeable.

Where the typed reason pays off

Acting on a category-specific field with the sealed-sum design is a type switch with typed fields: 

switch r := err.(*ressrf.BlockedError).Reason.(type) {
case *ressrf.InDenyCIDR:
    log.Warn("blocked by CIDR", "cidr", r.CIDR, "source", r.Source)
case *ressrf.SchemeNotAllowed:
    log.Warn("blocked scheme", "scheme", r.Scheme)
}

vs. the PR's flat string with the CIDR stuffed into a free-text field:

if be, ok := err.(*ressrfstatic.BlockedError); ok && be.Reason == ressrfstatic.ReasonIPDeniedByCIDR {
    log.Warn("blocked by CIDR", "cidr", be.DetailText) // string, no Source tier
}

The PR's flat string reasons are simpler to wire to JSON audit logs and mirror the Rust serde shape, but lose compile-time exhaustiveness.

The cloud-provider design is the most interesting divergence

PR #25's sub-package split (import "cloud/aws") lets the linker tree-shake unused datasets — they report 3.2 MB saved when only AWS is needed (Azure JSON alone is 108k lines). This repo embeds all cloud data unconditionally via codegen (internal/engine/cloud_generated.go), so binary size is constant. PR's approach is strictly better on size but requires more imports per call site. This repo's CloudProvider value type is more ergonomic for runtime/config-driven selection (single ParseCloudProvider boundary; the zero value is the only invalid state).

Insight
Diffuzz vs. fixed parity vectors is the most important testing-strategy gap. Fixed vectors prove known equivalence; the diff fuzzer proves random equivalence. The PR explicitly takes the trade — its parity gate runs in-CI without external toolchains, while diffuzz needs Rust + cargo + wasm32-wasip1. This repo isolates that cost behind the diffuzz build tag and a make fuzz-rust entry point, so the default go test path stays lean. Vectors catch known SSRF tricks; the fuzzer catches the third parser divergence you didn't know existed.

PR's parity gate is strictly cheaper to run (no Rust toolchain, no WASM compile) but can only catch divergences on URLs already in ssrf_techniques.json. Once the PR lands, adding diffuzz-on-the-static-port would close that gap.

The native fuzz targets in internal/engine/*_fuzz_test.go are also missing from the PR. For a security-critical parser these are cheap insurance — go test -fuzz=FuzzCIDR -fuzztime=30s finds malformed-input crashes the vectors will never enumerate.

3. Performance

PR's published numbers (-benchtime=5s on M1 Max, native vs. WASM in the same repo):

Op Native (static) WASM Speedup
PolicyBuild 56 µs 7.8 ms ~140×
IsAllowed (allowed) 1.29 µs 2.40 µs ~1.9×
IsAllowed (blocked) 815 ns 3.08 µs ~3.8×
IsNetworkAllowed 481 ns 1.51 µs ~3.1×

That comparison is WASM vs. native within the PR's own repo — not this repo vs. the PR. Both Go ports should be in the same order of magnitude on IsAllowed. They diverge on data structure:

  • PR #25 CIDR uses a hand-rolled [16]byte network + [16]byte mask + uint8 prefixLen with an inline 16-iteration AND-compare in Contains.
  • local uses netip.Prefix.Contains (one function call, no allocation) and netip.AddrFrom16(addr.As16()).

Both are linear scans (~30 entries in the IANA set) — the README notes the linear scan beats trees because of cache locality at this size. Likely tie within noise on the hot path; the PR may shave a few ns on Contains by skipping the netip.Prefix indirection, but pays for it with string -> netip.Addr re-parsing in CIDRSet.Contains(ipStr string) where this repo's IsNetworkAllowedAddrs(ctx, []netip.Addr) lets dialers skip the round-trip entirely.

Insight
This repo's IsNetworkAllowedAddrs is a small but real win for the TCP Control hook hot path: the syscall.RawConn callback already has a net.SplitHostPort + netip.ParseAddr; passing the parsed netip.Addr straight in avoids re-parsing inside the engine. The PR's IsNetworkAllowed([]string) forces a stringify-then-reparse on every dial. At dial frequency this is irrelevant; at 100k req/s it matters.

Binary size

PR wins decisively for selective-cloud consumers (3.2 MB saved when only AWS is needed). This repo always links all three cloud datasets via the cloud_generated.go codegen path. If size matters more than the simpler import surface, the PR's cloud/{aws,azure,gcp} split is the model.

Allocation profile

PR's validateAddresses does make([]string, len(ips)) + copy in emitHostValidated on every check — but the if p.auditSink == nil returns first, so this is moot in production (with-sink path does allocate per call). This repo emits with []netip.Addr and only stringifies inside the emit helper after the nil-sink early return. Equivalent on the no-sink path.

4. Security

Both engines implement the same Rust core's BS-1..BS-6 URI bypasses, ambiguous-IP rejection (octal/hex/decimal/shorthand), userinfo bypass guard, IPv4-mapped IPv6 normalization, and post-DNS Control-hook re-check. Where they diverge:

Concern local ressrf-go PR #25 ressrf-static
Allow-list mode flip visibility explicit separate constructor NewAllowListPolicy — code reviewer scanning options chain knows NewPolicy is deny-only implicit — WithTrustedSuffixes(...) flips mode by being non-empty; same builder for both shapes
Unknown preset handling rejected at construction with ErrUnknownPreset. Doc-comment explains the failure mode: a bad cast or future preset would silently map to PresetNone (permit-all). falls through checkOneIP's default: and returns a fmt.Errorf per-IP. Every IP fails with a non-BlockedError; callers using errors.Is(err, ErrBlocked) see false and treat it as a transient error, not a policy denial.
Cloud-provider typo handling ParseCloudProvider returns ErrUnknownCloudProvider at parse boundary; hard-coded sites use sealed exported vars (typo = compile error) WithCloudModule(aws.Module()) — typo is also a compile error (better here). String-named providers don't exist in this API.
Engine→Blocked error coercion typed via toBlockedError: if the engine returns something not implementing DenyReason, it falls back to Detail so errors.Is(err, ErrBlocked) still holds. Doc calls out the prior bug: an unchecked type assertion that would panic if a future engine change wrapped the rejection. direct err.(*BlockedError) assertion in validateAddresses — if checkOneIP ever returns a non-*BlockedError (the default: branch already does), this panics.
Audit-sink failure handling sinkAdapter.Emit substitutes a marker payload when JSON marshal fails, with comment "audit gaps are the failure mode this library exists to prevent" typed event structs — no JSON marshalling at emission time, so the failure mode doesn't exist (better by construction)
Audit ordering under concurrency sinkMu sync.Mutex serialises emission so concurrent callers see in-order events no mutex around p.auditSink.Emit(...); doc says "implementations must be safe for concurrent use" — pushes the requirement to the user
Allow-list construction safety NewAllowListPolicy rejects empty slice with ErrEmptyAllowList — "an empty allow-list would reject every non-IP host" non-empty check is the only mode signal — passing WithTrustedSuffixes() accidentally with zero args is a silent no-op
Redirect cap 10 hops, typed ErrTooManyRedirects constant 10 hops, returns fmt.Errorf("...too many redirects (max 10)") — un-errors.Is-able
Plaintext-HTTP downgrade always rejected toggleable via WithAllowPlaintextHTTP(bool) (matches Rust ProtocolRules; default = reject)

Insight
The "implicit mode flip" / "unknown preset silently permits" / "empty allow-list = no-op" cluster matters more than it looks. SSRF protection fails in one direction: a permit-all bug is a vulnerability; a deny-all bug is a 5xx. Every one of this repo's explicit-construction guards (NewAllowListPolicy rejects empty, buildPolicy rejects unknown preset, toBlockedError keeps errors.Is(ErrBlocked) true even on adapter errors) is a deliberate tilt toward "fail closed when misconfigured." The PR is mostly equivalent on the validator itself but is missing the construction-time guards — easy to add post-merge.

Bottom line

The PR is a clean port and pulls its weight as an alternative to the WASM-backed sibling. It wins on binary size (tree-shakable cloud sub-packages) and import surface (one package, no internal/). This repo wins on type safety (sealed-sum reasons, opaque CloudProvider, separate allow-list constructor), testing depth (native + differential fuzz, drift gates), and construction-time misconfig detection (unknown preset rejected, empty allow-list rejected, audit marshal-failure handled).

Most differences are addable in either direction. The tree-shakable cloud split is the one design choice that's structurally hard to retrofit (it forces an import cycle break — see PR's cloudmod package — that you'd need to mirror). The diffuzz harness and native fuzz targets are the easiest wins to upstream into the PR if it lands.
